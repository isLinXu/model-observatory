# 代码审查

审查一段改动的目标不是显得严格，而是**让正确的改动更容易合入**。

## 只报这三类

1. **错误**：逻辑与作者意图不符，或在边界输入下会失败。
2. **风险**：缺少必要的测试、错误处理或迁移步骤。
3. **不一致**：与仓库既有约定冲突（命名、错误处理、目录结构）。

风格偏好不是审查意见，除非它违反了项目已有的规范。

## 每条意见的格式

```
[级别] 文件:行号
现象：…
依据：具体输入 / 具体行 / 具体规范
建议：最小改动
```

级别只用 `blocker` / `suggestion` / `nit`。

## 纪律

- 每条意见都要能指出**具体位置**。无法定位的意见不要提。
- 如果无法判断对错，先提问而不是断言。
- 如果改动是正确的，直接说明通过，不要为了凑数加意见。
- 作者解释了设计选择后，不要重复争论同一个点。
